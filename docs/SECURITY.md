# Security and privacy

This app holds personal data that can hurt people if it leaks: who is travelling, where they will sleep each night, which flight they are on, and the codes that let anyone change or cancel a booking. Security is a top priority, above features and above schedule. Every change is reviewed for it, and a failing security check blocks a merge.

## What we hold

| Data | Where | Why it matters | Who may see it |
|---|---|---|---|
| Names, emails | users, travelers | Identity | Trip members |
| Itinerary: flights, hotels, addresses, dates, times | items | Physical whereabouts: where someone is and when the home is empty | Members who can see the item; view link visitors see `everyone` items only |
| Confirmation codes, booking references, seats, phone numbers, prices, booking sites | item_private | Enough to change, cancel or steal a booking | Owners and editors only, never viewers, view links, the calendar mirror by default, or logs |
| Hidden items | items with visibility only_me or specific | Surprises, private plans | Only the people chosen, not the owner |
| Imported raw records (emails, calendar events) | imported_items.raw | May contain everything above and more | Editors of the trip |
| Google refresh tokens | google_connections | Access to the user's Google calendars the app created | Nobody; encrypted at rest |
| Session, invite, view link, assistant tokens | cookies, hashed columns | Account and trip access | Nobody; only hashes are stored |
| Travel tip settings (tips on, kinds off, intro seen) | users | Preferences only, no trip data; read and written only for the signed in person, in their data export, deleted with the account | The person themselves |
| Activity log | activity | Before and after copies of items | Filtered by the same projection as items |

## Rules

1. **One permission boundary.** Every read goes through `projectTrip`; every write checks permissions in the service. No endpoint, page, feed, mirror or assistant tool reads the aggregate directly.
2. **Least data.** Collect only what a feature needs. Don't copy sensitive fields into new places (search indexes, logs, analytics, calendar events, PR text) without a reason written in docs/ARCHITECTURE.md.
3. **Secrets are hashed or encrypted.** Tokens are 32 random bytes, shown once, stored as SHA-256 hashes, compared in constant time. Secrets that must be read back (Google refresh tokens) use AES-256-GCM with a key from the environment. Sensitive booking fields, activity snapshots and imported records are encrypted at rest too, and imported free text goes only into the sealed private notes.
4. **No personal data in logs, errors or URLs.** Log ids and outcomes, not names, addresses, codes or raw imports. Error messages to users say what to do, never echo stored data. Personal data never goes in query strings. Assistant links carry a token, never personal data.
5. **Every input is parsed.** HTTP bodies, server action form data, assistant tool input, calendar events, emails, OAuth responses and files are parsed with zod (or the import pipeline) before use. Unknown fields are dropped.
6. **Outbound calls are explicit and minimal.** The app sends data to: Google (only the calendar it created, only the fields the mirror needs, no codes or seats by default); Google and Apple sign in (their OAuth endpoints, identity scopes only, never calendar access; provider tokens are not stored); only when `EMAIL_API_KEY` is set, the email API (`api.resend.com`: to, from, subject and the sign in link, nothing else); and, only when `ADDRESS_LOOKUP` is set, OpenStreetMap (an address string, no names or dates). In CI only, after an owner requested production deploy, the `prod-smoke` workflow requests three fixed paths (`/sign-in`, `/offline` and a bogus `/v/` link) on the pinned production alias `trip-planner-lilac-six.vercel.app`; it sends nothing but a fixed user agent and follows no redirects. Also, when an editor imports a calendar from a link (`src/server/import/fetch-guard.ts`), a GET to the https address they paste and to its redirects: https only, no user name, password or port in the address, the name resolved once and every resolved address required to be public (private, loopback, link-local, carrier-grade NAT, multicast, documentation and cloud metadata ranges, including IPv4 mapped and 6to4 forms, are refused) and the connection made to that checked address, each redirect checked again with at most 3 followed, 10 seconds in total, 2 MB at most (counted as it streams), no cookies or other credentials sent, and a response's cookies are ignored (only its status, its length and a redirect's location are read). The link path is switched off until its per person rate limit rule (`icsUrl`) exists: without that rule it refuses to run and fetches nothing. The address is used once: it is never stored, logged, put in an error or put in a URL. `webcal://` and `webcals://` links are treated as `https://` and get the same checks. Uploaded .ics files go through the same parser, are capped at 2 MB (counted in bytes while the upload streams in, whether or not it declares a length), and are never stored; only the proposed items reach the sealed review inbox. Any new outbound call needs a line in this file.
7. **Sessions and cookies.** HttpOnly, Secure in production, SameSite=Lax, signed, expiring. Sign out clears them. Sign in never asks for calendar access.
8. **Abuse resistance.** `src/proxy.ts` runs on every request except static assets. It sets a per request CSP nonce (`script-src 'self' 'nonce-...' 'strict-dynamic'`, no `unsafe-inline` or `unsafe-eval` for scripts in production, `frame-ancestors 'none'`, `base-uri 'none'`, `object-src 'none'`), HSTS in production, `X-Content-Type-Options: nosniff`, `Permissions-Policy` denying camera, microphone and geolocation, and `Cross-Origin-Opener-Policy: same-origin`. `/v/` and `/invite/` also send `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex, nofollow`, and `/v/` also sends `Cache-Control: private, no-store`. The visitor page keeps the visitor's device time zone in a short lived cookie `tp_zone` (path `/v`, SameSite=Lax, 24 hours), set by the page's own script; the server parses it as an IANA zone name (length capped, falls back to UTC) and never stores or logs it. Turning the view link on, making a new link and the two deadline switches are owner only on the server; turning on and making a new link share a per person limit of 20 per minute (rule `viewLinkChange`). In development only, `frame-ancestors` allows the phone frame on `http://localhost:8766`. Rate limits (fixed windows in the `rate_limits` table) apply to sign in (`/api/auth/signin`, `/callback` and `/email` in the proxy, and inside the Google, Apple and email link sign in actions themselves, wherever they are posted: one shared budget of 10 per 15 minutes per client address; other actions, such as sign out, spend nothing), invite acceptance (`/invite/`: 20 per 15 minutes), view links (`/v/`: 120 per minute), calendar feeds (`/api/feed/`: 60 per minute) and the assistant (`/api/mcp`: 120 per minute). Signed in actions have per person limits keyed on an HMAC of the user id: quick add 30 per minute, invite creation (every create from the Share page, including picking a person) 30 per minute, place hints 60 per minute, adding a traveler 30 per minute, data export 6 per 15 minutes, assistant links (`assistantLink`) 10 per hour, every idea change (`ideaChange`, in `ideaAction`) 60 per minute; over the limit the form says to wait instead of a 429 (the export download answers 429 with `Retry-After` and fixed plain text, or 503 if the limiter cannot be reached). Over the limit the response is 429 with `Retry-After` and fixed plain copy. Keys are HMAC-SHA-256 (keyed with `SESSION_SECRET`) of the rule name and the client address, so a leaked table cannot be matched against the IPv4 space; IPv6 clients are keyed on their /64. Raw addresses, emails and tokens are never stored. If the limiter cannot reach the database the response is 503 with the security headers (the sign in actions instead refuse with their fixed failure message), never an unlimited request. The client address is read from `x-forwarded-for` only when `TRUST_PROXY=1` (use the rightmost hop, which the trusted proxy appended). Without it, Next.js lets clients supply that header, so all clients share one bucket instead. Set `TRUST_PROXY=1` in production behind Vercel. Production refuses to serve (every route answers 500 with the setup message in the server log) unless `TRUST_PROXY` is `1` or `0`; `0` is only for a single user setup, because every client then shares each budget. The proxy also sets `x-request-path` (path and query of the real request) on every forwarded request, replacing any value the client sent; sign in redirects read it only through `safeNextPath`.
9. **Deletion is real.** `src/server/services/deletion-service.ts` is the only place that deletes a trip or an account. Deleting a trip (owner only) first deletes each member's Google calendar the app created (`teardownMirror`), then in one transaction removes every table in `TRIP_DATA_TABLES` for the trip (items and their private fields and deadlines, imports, activity, check dismissals, assistant tokens scoped to the trip, invites, view link, travelers, memberships, calendar mirrors and their event maps) and the trip. If Google refuses, nothing is deleted and the owner can retry; if Google is not configured, the member has disconnected Google, or Google refuses access because they revoked it, the app cannot reach the calendar: the mirror row is dropped, deletion continues, and the calendar stays in the member's Google account for them to delete there. A test fails when a table with a `trip_id` column is missing from `TRIP_DATA_TABLES`, so every package that stores trip data extends that list. Deleting an account is refused while the user owns a trip that has other members (the response names those trips); otherwise it deletes their solo trips, memberships, mirrors and Google calendars, Google connection, sessions, sign in accounts, assistant tokens, pending sign in links for their email, invites they created, and the account. All Google calls happen first and any failure other than refused access stops everything before account data is touched; then one transaction re-checks that no owned trip gained members, deletes owned solo trips and removes the account. In trips that stay, their visible items, activity, imports and dismissals are handed to the trip owner (the other copies of their id are cleared). Hidden items are never handed to anyone who could not already see them: their only me items are always deleted, their specific items pass to the first person on the visible-to list who stays on the trip (deleted if none), or are all deleted when they choose; the activity rows and approved imports of every deleted item go with it. Rate limit rows are keyed by an HMAC of the client address and hold no user id, so they need no per person deletion and expire on their own. A test fails if any table that points at users still holds a row for a deleted user. Deleting an account also resyncs the Google calendars of the members who stay, so a deleted hidden item leaves their calendars at once. Google errors are classified by reason (rate limit, quota and unknown 403 errors stop the deletion and change nothing; forbidden, insufficient permission, 401 and `invalid_grant` drop the mirror and carry on), and Google's response text is never put in an error message. Export of a user's data is `exportUserData` in `src/server/services/export-service.ts`, reached only by a POST to `/account/export` that needs a same-site `Origin` and a session: it returns what `projectTrip` lets the person see plus their own private rows, as an attachment named by date only with `Cache-Control: no-store`, and never other people's hidden items, ids, emails, hashes, tokens, links or invites. The one time lines after a deletion are an HttpOnly cookie that holds only the kind of line, never a name.
10. **Dependencies are audited.** CI runs `npm audit` for production dependencies at high severity. New dependencies need a reason.
11. **Test data is fake.** Fixtures and demo trips use placeholder codes and phone numbers. Never commit real booking codes, phone numbers, emails or tokens. The repository is public, so nothing secret is ever committed. The Vercel ignore script (`tools/ci/vercel-ignore.sh`) reads a commit's status from the GitHub API without a token, which works only because the repository is public; if it were made private the call would be refused and production would never build (it fails closed). Only a `deploy/approved` status created by `github-actions[bot]` counts.

## Threat model (short)

| Threat | Mitigation | Proven by |
|---|---|---|
| A viewer or link visitor reads codes or hidden items | `projectTrip` strips them; tests assert they are absent from serialized output | `project.test.ts`, `calendar-mirror.test.ts`, `server.test.ts` |
| An editor edits or deletes an item hidden from them | `assertCanEditItem` | `services.test.ts` |
| A caller claims a role | `Requester` has no role; roles come from memberships | `project.test.ts` |
| A leaked assistant link | Hashed, revocable, trip scoped, read or propose only, proposals need human approval | `server.test.ts` |
| Stolen database | Tokens hashed; Google tokens, booking fields, activity and imports encrypted | `auth.test.ts`, `encryption.test.ts`, `import-secrets.test.ts` |
| An AI assistant is tricked into proposing bad data | Proposals only reach the inbox; a person approves | `server.test.ts`, `services.test.ts` |
| Brute forcing tokens or links | 256 bit tokens; rate limits on sign in (including the email link form), invites, view links, feeds and the assistant | `auth.test.ts`, `adapter.test.ts`, `rate-limit.test.ts`, `proxy-routes.test.ts`, `src/app/sign-in/actions.test.ts` |
| Open redirect after sign in | Every `next` goes through `safeNextPath`; the proxy overwrites `x-request-path` | `next-path.test.ts`, `web.test.ts`, `dev-routes.test.ts`, `proxy-routes.test.ts` |
| A Google calendar shared onward exposes codes | Mirror leaves codes out by default | `calendar-mirror.test.ts` |
| Personal data in logs | Rule 4; reviewed on every PR | security review |

## Review

Every pull request gets a security review (see `.claude/agents/security-reviewer.md`). A PR that touches auth, tokens, permissions, imports, outbound calls, logging or the database schema cannot merge with an open security finding of severity high or above.

## Reporting

If you find a problem, do not open a public issue. Tell the repository owner directly.
